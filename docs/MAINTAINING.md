# 维护规则

Postglow 装在用户的电脑上，并且会自动提示更新。所以「改代码」和「发版本」是两件事：改代码随时可以，发版本要有节奏。

## 三种动作

| 动作 | 影响谁 | 频率 |
|---|---|---|
| 本地提交 | 只有自己 | 随时，一个改动一个提交 |
| 推送到 main | 没有用户受影响（只跑 CI 检查；一行安装和应用内更新都只认 Release） | 随时，攒几个提交一起推也行 |
| 发布版本（打 tag + Release） | 所有用户：一天内收到更新提示 | 有节奏，见下 |

## 发布节奏

- **平时：攒一批再发。** 小修复、小改进先合进 main，写进 CHANGELOG 的「未发布」，大约每 1–2 周，或者攒够一批有感知的改动时，发一个版本。
- **紧急修复：当天发。** 只限于：应用打不开或崩溃、读取全部失败、数据丢失或损坏、安全问题。紧急版本只带这一个修复。
- 同一天不发第二个版本，除非上一个版本有紧急问题。

## 版本号

`0.x.y`：
- `y` +1：修复和小改进。
- `x` +1（`y` 归零）：新功能或较大的变化。
- 功能稳定、准备长期维护后再到 `1.0.0`。

## 每次改动

1. 代码改完，`npm test` 通过，`npm run dev` 里把相关功能点一遍。
2. 在 `CHANGELOG.md` 的「未发布」下面加一行，用用户的话写（「修复：窗口无法拖动」，而不是「加 capability」）。
3. 提交。

## 发布

```sh
scripts/release.sh 0.1.6
```

它会检查、测试、改好所有版本号、整理 CHANGELOG、提交、打 tag、推送，并用「未发布」那一节创建 GitHub Release。CI 随后构建 DMG、签名更新包、生成 `latest.json`。

发布后：
1. 等 CI 通过（`gh run watch`）。
2. 确认 `latest.json` 是新版本号。
3. 在本机旧版本里点「检查更新」，确认能更新过去。

### 发布前手动过一遍

- 欢迎页 → 输入用户名 → 读取成功
- 拖动窗口、关闭窗口（留在菜单栏 / 退出）、菜单栏图标的三个菜单项
- 右上角 **?** 使用说明、各处 **?** 悬停
- 安装窗口（DMG）的背景和图标位置，如果改过 `src-tauri/dmg/`

## 不要做

- **不要移动、删除或复用已经发布的 tag 和 Release。** 应用内更新依赖它们；有问题就发一个新版本。
- **不要删掉 Release 里的 `latest.json`、`.app.tar.gz` 或 `.dmg`。**
- **不要改 `tauri.conf.json` 里的 updater `pubkey`。** 改了之后，所有已安装的应用都无法再更新。
- **保管好更新签名私钥**：`~/.tauri/postglow.key` 和 `~/.tauri/postglow.key.password`，另有一份在 GitHub Secrets（`TAURI_SIGNING_PRIVATE_KEY`、`TAURI_SIGNING_PRIVATE_KEY_PASSWORD`），请再备份到密码管理器。丢失 = 已安装的用户再也收不到更新。

## 关于 macOS 的「已损坏」提示

没有 Apple 开发者账号（每年 99 美元），浏览器下载的安装包第一次打开一定会被 macOS 提示「已损坏」，需要在「隐私与安全性」里点「仍要打开」放行一次。整体临时签名（`signingIdentity: "-"`）也避免不了。一行命令安装和应用内更新不会出现这个提示。以后如果申请了开发者账号，在 CI 里加 Developer ID 签名和公证即可。
